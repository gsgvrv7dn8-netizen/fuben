调研日期：2026-10-24（北京时间）。本方案是工作提案，不是已经验证的最优算法或获奖保证。原始资料位于 `D:\MathorCup`；本次仅作阅读、数据核验和规划，尚未训练竞赛模型。

**建议采用三人协作：你用 Codex Pro 推进主线，B 用 DeepSeek 核验资料和提出反例，C 用 Codex Plus 独立复现、检查论证和交付。三人共享一个项目及一套验证标准。** 每个人都使用 AI，但问题定义、核心建模、算法设计、求解与分析仍需队员实质参与并独立完成。

## 2. 本地检查已经发现的高优先级问题

完整核验见 [数据初查](research/data-audit.md)。下面是影响架构的结论，而非一般性的风险提醒。

| 已确认事实 | 直接影响 |
|---|---|
| 1.csv 为 250 个样本、231 个化学/理化特征，另有 3 个元数据字段 | 是小样本、多特征问题；不应因赛事名称含“大数据”就先上大型模型 |
| 4.csv 有 50 个感官指标，其中 A_ 和 F_ 各 15 个 | 题面“约 40 维”需逐项映射，不能随意增删目标 |
| 3.xlsx 有 12 张空评分卡和 summary，汇总零值来自公式缓存 | 零不是实测标签；不能把表格刻度 0–6 当训练数据 |
| 当前附件未发现原始感官评分或明确的逆标准化参数 | 原始 0–6 尺度尚不能准确恢复；必须追溯来源或官方说明 |
| 4/7.csv 的 beer_id 只有 96 个唯一值，beer 有 250 个唯一值 | 按 beer 显式一对一连接并断言唯一性，防止错配扩行 |
| 2.csv 与按 1.csv 重算的 Spearman 矩阵误差约 6.66e-16 | 实际支持 Spearman，与赛题 PDF 的 Pearson 描述冲突 |
| pH、ethanol 等已核验列与 8.xlsx 校准值的 log10 对应 | 不能照题面把这些列直接当原始物理量；也不能统一给所有列做指数反变换 |
| 8.xlsx 有来源实验的 GBM/SHAP、阈值与校准化学表 | 参考结果与本队实验必须区分；阈值须先核实单位与名称 |
| 22 个风格中最小类别只有 3 个样本 | 分层验证和按风格生成都要处理小类别，不能机械套默认设置 |

对评分尺度，尤其要避免“把最小值映射成 0、最大值映射成 6，所以恢复了原始分数”的推断。这样的映射可以是有明确假设的估计，但不是恢复真实评分；也无法凭现有标准化标签证明其原尺度误差。

已找到与附件背景和结构高度吻合的原始研究《Predicting and improving complex beer flavor through machine learning》（2024）及作者公开的数据/代码仓库。它们适合追溯变量、变换及实验设计；仍需逐项核对与赛事附件的版本和加工差异。该研究比较了多类模型，梯度提升表现突出，但这不意味着它必然是本赛最优方法。[论文](https://www.nature.com/articles/s41467-024-46346-0)；[作者数据与代码](https://zenodo.org/records/10653704)

## 3. 三人如何分工

| 成员与现有工具 | 主责任 | 每轮应交回的内容 | 队员需实质参与的工作 |
|---|---|---|---|
| 你：Codex Pro 20x | 总控协调、主线实现和实验整合 | 可运行版本、实验表、当前候选、待决策事项 | 定义主问题，理解并决定方案及其取舍 |
| B：DeepSeek | 原始资料、公式与单位核查，提出反例，审阅模型假设 | 原文链接/页码、事实与推断、冲突、可验证的反对意见 | 读原文、检查假设、参与核心方法推导 |
| C：Codex Plus | 独立复现、数据泄漏和边界检查、图表与论文证据、交付演练 | 复跑命令与结果、失败清单、结论对应的证据位置 | 独立判断实验是否成立，核查解释与交付 |

这是根据你提供的工具配置作出的初始分工，不是对三个模型能力或额度的排名。B 若只有聊天界面，就接收精简、可核验的证据包；需要执行的检查交给可运行代码的环境，不能让语言回答充当执行结果。C 的工作从第一天开始；文稿负责人也应参与建模和分析，不能只是最后润色。

三人共同决定问题定义、评价指标和最终结论。任务重时可轮换所有者，但重要结果由另一人复核。两个 Codex 同时工作时分配不同文件/分支，避免同时重写同一核心模块。共享同一数据版本，不各自清洗出三套互不兼容的数据。

你们尚未提供技能基础、可用时长与电脑配置，因此本方案不假设有 GPU、能通宵或具备特定统计基础，也不承诺运行速度。先通过一次小规模基线实测再分配计算预算。

## 4. AI 应按“有验收的任务”使用

可借鉴的证据并不支持把聊天轮数当进度。AIDE 将方案组织成候选树，用真实执行结果选择改进方向，并限制排错；Anthropic 的实践强调先用简单结构，复杂度要由实际收益支持。2026-10-22 的文章进一步建议随评测调整子 agent 边界。[AIDE](https://arxiv.org/html/2502.13138v1)；[Building effective agents](https://www.anthropic.com/research/building-effective-agents)；[何时合并子 agent](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

MLE-bench 和 MLAgentBench 评测的是读取数据、执行代码、训练和检查结果的完整能力。它们证明这类工作可以被系统评测，但旧模型的历史分数不能当作本届获奖概率，也不能证明某种三人分工一定更优。[MLE-bench](https://openai.com/index/mle-bench/)；[MLAgentBench](https://proceedings.mlr.press/v235/huang24y.html)

本队每轮采用：**队员提出可检验假设 → agent 辅助实现 → 真实运行 → 按共同标准比较 → 另一成员复核 → 队员决定保留、修正或放弃。**

任务卡只需这些字段：

```text
任务编号与负责人：
要检验的假设 / 要澄清的事实：
输入文件与版本：
允许修改的模块：
必须保持的评价口径：
预算：候选数量、运行时间或交互轮数上限：
交付：代码/来源、真实日志、结果表、失败案例、局限：
验收：如何判定完成，谁独立复核：
停止条件：达到预算、无稳定收益，或发现口径错误时汇报：
```

例如，当前适合的任务是“核对某列在 1.csv 与校准表之间的变换，输出有效样本数、误差与反例”，而不是“帮我把三问做完”。研究任务也必须交来源、页码和未解问题，不能只给一段自信的结论。

初期每条思路可限制为少量候选及两轮修正；这是建议起点，待实测调整。一次尽量只改一个主要因素。没有真实运行就标为“待验证”，失败实验也保留，防止其他成员重复踩坑。不同模型意见相同不等于验证通过，独立代码执行和证据检查更有价值。

## 5. 可以改变的最小架构

本对话负责当前目标、任务顺序、疑点、决策与验收；具体执行按需拆任务。长期记忆保存在文件中，聊天记录不作为唯一状态来源。

```text
三人共同确定问题、假设与评价标准
                ↓
本对话总控：排优先级、分配任务、记录决策
                ↓
共享项目：原始数据引用 / 数据字典 / 代码 / 实验表 / AI记录
                ↓
数据与尺度核查 → 可复现基线 → 候选改进
                ↓
统一评价 + 独立复核 → 保留 / 修正 / 回退
                ↓
论文、图表、代码和提交包
```

先约定少量稳定接口：样本键、字段名与单位、目标映射、验证划分和指标、结果文件结构。内部模型、特征处理、解释方法、生成方法和 agent 分工都可改变。实现先用少量 Python 模块和配置文件；不需要先搭数据库、消息队列或大型 agent 平台。

建议的概念模块是：读取与校验；预处理与特征；感官预测；0–6 分级校准；相关图与解释；风格生成/迁移；评价与导出。它们不要求一开始就是七套复杂软件，只需要边界清楚。尤其把预测和分级校准分开，避免评分口径变化迫使重写所有模型。

**容错通过版本和回退实现：**

- 每个可提交基线保留代码、配置、数据版本、运行命令和输出。新实验不覆盖它。
- 并行任务登记负责人和可修改文件，回传短摘要与产物路径。
- 数据或验证口径有错误，升级其版本并重跑主要候选；旧、新口径分数不直接比较。
- 有跨模块影响的修改先记“为什么改、影响什么、回退到哪里”，再实施。
- 每天一次简短合并：今天证实了什么、推翻了什么、下一个最大未知是什么。

只在出现具体瓶颈时改变架构：上下文常丢失就补交接文件；重复实验就加强台账；互相传话造成错误就合并任务；独立工作排队才增加并行；新模块没有可测收益就撤回。不要为“以后可能需要”提前增加层级。

## 6. 三问的方向与验收

以下是供队员理解、比较和决定的候选方向，不是已确认方案。

| 题目 | 先做的最小方案方向 | 后续可替换处 | 内部验收重点 |
|---|---|---|---|
| 问题 1：感官评分 | 先明确目标和尺度；比较均值等朴素基线、正则化/PLS 与树模型等少量候选 | 缺失处理、预测器、0–6 校准分别替换 | 折外预测、逐维误差、缺失敏感性；分级映射有依据，无法识别的尺度明确披露 |
| 问题 2：Top-3 化合物 | 相关图与预测重要性结合，加入重采样稳定性和化学证据 | 选边阈值、相关特征处理、解释方法 | 每个维度确有 Top-3、入选稳定性、名称与单位可追溯；相关不冒充因果 |
| 问题 3：生成与迁移 | 先比较小样本适用的风格条件统计生成方法，显式加入缺陷约束 | 生成器、迁移目标和约束实现 | 风格相符、范围/相关结构合理、输出有多样性、无明显训练样本复制、迁移前后缺陷约束可核验 |

第三问要求学习条件生成模型，单纯复制风格均值或机械改变几个数只能算基线/对照，不能冒充完整完成。若再尝试复杂生成模型，必须以相同指标证明价值。小样本是否支持其复杂度，应由实验判断。

“生成得像”不代表能实际酿造或会更好喝。没有实验品评就只能报告模型层面的合理性。缺陷项存在名称、单位或阈值空缺时，应报告可评价覆盖范围，不能编造阈值或宣称全部不恶化。

三问共享数据和部分模型，但不能形成自证循环：不能只让同一预测器生成目标，再只用这个预测器证明目标实现。应结合未参与优化的统计检验、独立验证或来源阈值，报告未被独立证明的部分。

## 7. 验证与实验记录

样本只有 250 个，应先设计与任务目标匹配的验证。先划分再拟合插补、缩放、特征选择等；有重复/分组就按相应单位隔离。小类别能否分层需检查。可采用交叉验证与独立检查，但不要机械固定五折、二八划分或时间切分。[scikit-learn：常见陷阱](https://scikit-learn.org/stable/common_pitfalls.html)；[交叉验证](https://scikit-learn.org/stable/modules/cross_validation.html)

附件 2 是全样本 X 的相关图；用于描述可如实说明，若把图用于折内建模则应区分其全数据信息影响。附件 5/6 涉及目标，8.xlsx 中重要性/SHAP来自现成模型；不能拿涉及验证样本目标的信息筛特征后再宣称验证独立。评测路径中的数据依赖要记录清楚。

每次实验至少记录：编号、负责人、假设、数据版本、代码版本、验证版本、参数/随机种子、指标、耗时、输出路径和复核结论。结果不只存平均分，还保存各维度、各折及重要失败样本。论文数字和图表必须能指回实验编号。[MLflow 的记录要素](https://www.mlflow.org/docs/latest/tracking/)可参考，但初期用 CSV/JSON 即可。

Kaggle 的验证经验有借鉴意义，例如获奖者对验证与排行榜差异、失败方法的复盘；本赛尚未证实有该类排行榜，不能照搬其提交流程或把某模型获奖经验当保证。[获奖者本人方案](https://www.kaggle.com/competitions/learning-agency-lab-automated-essay-scoring-2/writeups/flg-1st-place-solution-trust-cv-and-lb-a-bit)

## 9. 当前就采用的总控约定

1. 本对话管理方向、任务和结果验收；跨成员交接以文件和短报告为准。
2. 当前状态写入 [CONTROL.md](CONTROL.md)；长期证据在 research，后续实验存独立目录。
3. 所有结论标识为“已核验 / 待验证 / 假设 / 已否定”。正式文稿中区分这些状态。
4. 不把任务口头完成当作完成：必须交付可读来源或可复跑产物。
5. 从本次调研开始保存 AI 使用信息；精确模型、关键交互与人工贡献如实补全，不能倒填或虚构。

最初要做对的是数据解释和评价，而不是提前选出终局算法。架构的作用是让发现错误后能够局部修正、重新比较，并保留已经验证的工作。

## 10. 推荐阅读顺序与调研边界
