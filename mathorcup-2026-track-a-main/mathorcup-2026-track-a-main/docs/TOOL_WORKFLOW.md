# 工具驱动的比赛工作流

这是用户明确要求的执行规范：不能只进行AI问答。每项任务选择适用的skill、脚本、浏览器、表格软件或其他工具，并留下真实操作证据；未执行的分析只能标为待验证。skill用于组织工作，不能替代数据和实验。

## 共同闭环

**问题与证据 → 可证伪假设 → 适用skill/工具 → 实际操作 → 可复跑产物 → 独立检查 → 队员决定。**

开始任务时说明选择的skill/方法与理由。环境支持skill时，读取对应SKILL.md再使用；不可用时记录限制，采用等价工具流程，不能声称已调用。不得为凑“用了skill”的数量安装复杂平台或运行无关扫描。

## 各成员最低执行要求

| 成员 | 适用技能/流程示例 | 必须实际使用的工具与证据 |
|---|---|---|
| A：实现 | mle-workflow、Python实现/测试、代码审查 | 终端运行Python、数据校验、真实训练/评估、必要pytest、Git差异；交命令/环境/日志/指标/产物 |
| 刘源B：证据 | deep-research或科学文献检索、PDF/表格读取、来源交叉核查 | 浏览器真正打开原文；PDF页码/章节；Excel或Python检查单元格与公式；关键数值有计算过程；交证据表与反例 |
| 谢小鱼C：验收 | mle-workflow检查清单、Python测试、独立复现、论文证据审查 | 独立工作副本执行RUNBOOK与测试；核对哈希、划分、指标；Git diff/PR审阅；交命令与实际差异 |
| 总控 | 调研、GitHub协作、证据与决策记录 | 读取实际产物/PR/状态；分派可验收任务，保存版本与决策；不把其他agent自评视为验收 |

以上是适用示例，不要求三人的环境都有相同插件。DeepSeek只有聊天功能时，刘源本人用浏览器、Excel或本地脚本完成工具步骤，把核对结果回填证据表；也可把明确的计算子任务交给A/C运行，记录执行者。工具无法使用时写受阻与替代方法，不伪造已执行。

## 一个任务的工具记录

使用`templates/tool-task.md`，记录关键操作即可，不要求复制所有终端输出：

- task_id、负责人、目标与验收标准。
- 实际采用的skill名称/来源/版本（未知注明）、方法依据、能力限制。
- 输入文件与哈希或来源链接。
- 关键工具、命令/操作、执行日期、结果/失败。
- run_id、日志、截图/单元格证据、输出文件路径。
- 独立检查人或agent及检查范围，队员实际决定。

可保存到`records/tools/A/`、`records/tools/B/`、`records/tools/C/`，也可在现有run manifest/证据表中提供等价字段并链接，避免重复抄写。独立agent审查与队员本人审查分别标注。

## 无效完成与有效完成

- “模型说这个公式正确”是待验证；原始定义、计算推导和数值反例检查是证据。
- “代码看起来能运行”是待验证；命令成功、输出存在且内容检查通过才算可执行。
- “得分更高”需要相同划分/指标/数据版本及真实日志，不能由语言模型猜测。
- “已复现”需要重新执行并比较，不能仅阅读A的输出。
- 失败实验不等于失败工作；能复现的失败原因和下一条可检验假设是有效交付。

## 采用的工程经验

轻量采用mle-workflow的数据契约、可复现流水线、评价门槛和回退记录；不引入本赛不需要的在线服务、特征库或发布监控。借鉴[AIDE](https://arxiv.org/html/2502.13138v1)的候选实验与执行反馈、[scikit-learn防泄漏说明](https://scikit-learn.org/stable/common_pitfalls.html)的训练/验证边界。这些方法服务于本届赛题和规则，不取代队员独立建模要求。
