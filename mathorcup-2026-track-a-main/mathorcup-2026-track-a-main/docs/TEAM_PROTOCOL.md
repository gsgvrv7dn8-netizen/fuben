# 三人统一工作规范 v1

更新时间：2026-10-24。适用于人、聊天、agent和脚本。规范是协作起点，可经总控记录理由后升级。

**工具执行是共同要求。** 先读[工具工作流](TOOL_WORKFLOW.md)：按任务选择skill/工具，实际阅读、计算、运行、测试和复查；交回操作证据，不以连续AI问答或自评作为完成。采用的skill、关键工具和能力限制可记录在现有manifest/证据表，或使用templates/tool-task.md。

## 1. 共同事实与版本

- 时区统一 Asia/Shanghai；时间写ISO格式带`+08:00`。UTC机器时间可额外保留。
- 文件编码UTF-8；CSV首行字段名，不以Excel显示格式作为数值依据。
- 代码/文档按.gitattributes使用LF；证据CSV和已哈希的结果JSON保留原始字节，避免跨系统换行转换破坏校验。
- 数据路径通过配置传入；原始资料不修改。文件SHA-256作为数据身份。
- 样本使用已验证的`beer`键；每次检查唯一性、缺失键及一对一连接，不能只凭行顺序。
- 字段名称保留原文并维护显式别名映射；不自动把相似化合物名合并。
- 目标、单位/变换、验证划分、指标分别有版本或文件哈希。未知就是unknown，不能省略后默认已确认。

## 2. 记录类型与最低字段

| 记录 | 最低内容 | 保存处 |
|---|---|---|
| 证据 | 编号、待证主张、来源URL/文件与位置、核查方法、结论、局限、核查人/时间 | research/B/或基础research报告 |
| 实验 | run_id、负责人、假设、数据哈希、代码版本/dirty快照、配置与seed、验证/指标版本、命令、环境、指标、日志和输出路径、状态 | runs/本地；摘要入reports/ |
| 验收 | 被验收提交/run_id、独立命令、预期/实际、差异、结论、验收者 | reports/C/ |
| 决策 | 问题、证据、可选方案、队员决定、影响范围、回退点、日期 | records/decisions/ |
| AI使用 | 工具及实际模型/版本、开发方、日期、环节、关键交互位置、采纳内容、真实人工修改/检查 | records/ai/成员/ |

run_id建议`A-20261024-001`等成员+日期+序号。实验没有Git提交时，保存明确的源码快照及哈希并标dirty；不能填写假的commit。JSON指标用数值，不把缺失指标填0；失败或不可评价写null并给原因。

## 3. 评价边界

- 先固定划分，再拟合所有可学习的预处理；特征选择、调参和挑选模型也遵守验证边界。
- 训练折预处理只看训练样本；独立验收不能依赖包含被验收目标信息的全样本统计。
- 预测标准化值、估计0–6分级、恢复真实原始打分是不同主张，分别评价。没有原尺度真值就不报告原尺度真实准确率。
- 报逐目标、逐折结果及样本数；总体指标不能掩盖某些维度失败。
- 生成/迁移报告风格、范围/相关结构、重复与多样性、缺陷约束覆盖率。单位或阈值缺失项不能算作通过。
- 模型拟合效果与化学因果不同；来源作者的现成结果与本队新结果不同，文稿明确标识。

## 4. 复现分级

1. **可执行**：命令跑通，输出存在。
2. **同环境可复现**：记录的输入/配置/seed下重跑，指标在预设容差内一致。
3. **独立验收**：另一成员按RUNBOOK在独立工作副本运行并核对结果。

三个状态分别记录；A自己重复运行不能自动标为C已验收。涉及非确定性算法时预先给容差和比较方法，不在看到差异后任意放宽。

## 5. Git与文件协作

- 仓库Owner必须为用户确认的echo1229；每人使用本人已获授权的GitHub账号操作，不共享登录。总控当前操作身份已核验为echo1229。仓库及邀请状态看CONTROL。
- 主分支main保存可理解、可复现的整合版本；每人在独立副本操作，不在多人并行过程中擅自切换他人工作区。
- 分支示例：`codex/a-baseline`、`codex/b-evidence`、`codex/c-review`；每人自己的克隆/工作副本中操作。
- 小步提交，一个PR围绕一项可验收结果。PR写问题、改动、验证、未解项和受影响版本。
- 不强推、不上传密钥、不把原始数据/模型缓存/全量运行文件塞进Git。轻量结果摘要、必要配置、来源清单和代码入库。
- 队员审批与GitHub是否提供付费保护规则无关：即使无技术强制，也按“一人提出、另一人核对”的约定执行。

## 6. 回传频率：少打断、有检查点

- **首次里程碑**：领到任务24小时内，B交证据表v1，C交独立验收方案和已能执行的检查；依赖缺失时说明缺口，不假装完成。
- **日常状态**：比赛期间每日（含周末）北京时间21:00前更新自己的`reports/X_STATUS.md`。正文最多约15行，链接到详细文件。当天21:00之后才开始，可先写启动状态，完整首批结果仍按24小时要求。
- **阶段回传**：完成里程碑后更新状态与证据，开/更新标题含`[待验收]`的PR，填写templates/handoff.md，按docs/GITHUB_HANDOFF.md交接。总控在PR评论验收与续派，B/C自行读取；不要求用户转发。
- **立即升级**：发现样本错配、数据泄漏、结果造假/不可复现、目标/单位根本错误、阻塞主线超过约2小时或影响截止时间。通过现有队内渠道告知用户，由总控更新任务；不需要堆长聊天。
- 其他一般问题在职责内处理，记录尝试与失败，继续不依赖该问题的工作。

用户要求不用定时任务。A完成后主动回报总控；总控每次收到A完成回报或主动执行项目工作时，一并检查B/C待验收PR。按仓库、PR编号和head SHA去重。GitHub事件目前不能直接唤醒这个桌面聊天，A与总控都停止时不保证即时验收。具体边界及可选事件入口见docs/GITHUB_HANDOFF.md。

## 8. 有效完成

任务完成需要产物、证据和局限，不以“agent说完成”作为依据。核心结论需要队员能解释并确认；AI对话中的自评不能代替人员独立完成要求。最终AI说明从过程记录汇总，不事后虚构人工贡献。
