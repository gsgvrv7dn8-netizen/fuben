# B/C 在 GitHub 交付、验收与续派

更新：2026-10-24，Asia/Shanghai。用户要求尽量免去传话，且不用定时任务。本文件把交接统一放进仓库；不宣称已经接通尚未配置的事件服务。

## 现在可用的流程

1. 刘源B与谢小鱼C各用自己的分支，保存职责内的证据、工具日志、AI记录和reports/B_STATUS.md或C_STATUS.md。
2. 完成里程碑后开PR；同一里程碑的小修复继续原PR。标题用`[B][M1][待验收] 具体成果`或`[C][M1][待验收] 具体成果`；受阻时将待验收改为受阻。正文使用templates/handoff.md，填真实head SHA，C额外写被检查的A版本与run_id。不把整个聊天粘贴到PR。
3. 总控每次收到A的完成回报、以及主动执行本项目工作时，检查本仓库待验收/受阻PR和成员状态。查看实际差异、证据、命令与局限，按`仓库 + PR编号 + head SHA`去重，不重复验收旧提交。
4. 总控把结论与下一阶段任务直接评论在相同PR：验收对应SHA、通过/需修复/受阻及依据、task_id与负责人、输入依赖、产物路径、完成条件、下次交接位置。影响长期职责或共同口径的决定再写入任务文档/决策记录。
5. B/C自己读取本PR最新反馈并执行，完成后更新原PR或开下一里程碑PR，无需队长转发。没有新反馈时，继续各自长期任务中不依赖验收的工作，不凭沉默认定通过。
6. PR有新提交，旧验收仅覆盖旧SHA；补交后恢复标题的待验收标识，并在正文/评论更新实际SHA。验收记录注明AI技术核查、人员独立复现或科学确认的区别。

B的DeepSeek若没有GitHub工具，由B本人在网页提交和查看评论；不能声称DeepSeek已自动接入。C先接受仓库邀请，使用自己的账号；本次CLI检查仍未见C出现在已接受协作者列表。

## 当前通知能力的边界

- A与总控在同一可访问环境，用户已授权A完成后直接发消息；具体见A任务中的回报协议。
- B/C的GitHub PR是持久的交接队列，但当前桌面聊天没有已配置的GitHub事件接收入口。A与总控都停止时，不能保证即时验收；目前未建定时轮询、常驻中转服务或GitHub Actions。
- `@echo1229`或请求GitHub reviewer不等于唤醒本聊天。`@codex review`属于另外的代码审查入口，不能替代实验复现、科学核验或当前总控的续派。
